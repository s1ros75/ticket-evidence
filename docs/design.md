# 設計メモ

## このアプリについて

1. 顧客の要件を調べて、開発向けにチケットへまとめる担当者が使う
2. 「確認済み」「不明点」「仮定」と「根拠」を分けて残し、レビューで聞かれても根拠をその場で示せるようにする
3. 不明点が残るチケットは、レビュー依頼に進めない。進み具合は一覧とダッシュボードで見える
4. 機能はしぼり、UIもシンプルに保つ。Redmineのような汎用のチケット管理は目指さない（違いはREADMEに書いた）

## 画面一覧

- ログイン
- チケット一覧（作成、ステータスでの絞り込み、不明点の残数）
- チケット詳細（項目の追加、根拠を付けた解決、レビュー依頼、完了・差し戻し、変更履歴）
- ダッシュボード（ステータス別件数、不明点が残る調査中のチケット数）
- アカウント管理（管理者だけ。アカウントの作成と仮パスワードの発行）
- パスワード変更

## テーブル

- users（名前、メール、パスワードのハッシュ、ロール：担当者/レビュアー、管理者かどうか）
- user_sessions（user_id、IPアドレス、User-Agent、最終操作日時）
- tickets（タイトル、概要、ステータス：調査中/レビュー中/完了）
- ticket_items（ticket_id、種別：確認済み/不明点/仮定、本文、解決日時）
- evidences（ticket_item_id、リンク、メモ）
- ticket_events（ticket_id、user_id、操作、変更前後などの内容（jsonb）、日時）

## ステータスの流れ

```
調査中 ──レビュー依頼──▶ レビュー中 ──完了──▶ 完了
  ▲   （不明点が0件のとき）    │
  └────────差し戻し───────────┘
       （理由が不明点として追加される）
```

## 決めたこと

### 項目と根拠

#### 確認済みと不明点を、同じテーブルで種別分けする
理由：不明点が解決したとき、データを移さず種別だけ変えられるため
他の選択肢：別テーブルにする（検索は楽だが、移動処理が必要になる）

#### 「解決する」ときに、根拠の入力を必須にする
理由：根拠を残すことがこのアプリの目的で、任意にすると空のまま残る可能性があるため
他の選択肢：任意にする（気軽に使えるが、根拠が残らない）
補足：負担を減らすため、リンクかメモのどちらか1つで通す。リンクは http/https だけを受け付ける（画面でリンクとして表示するので、`javascript:` などを入れられないようにする）

#### 仮定も、根拠を付けて解決すると確認済みになる
理由：仮定は「確認が取れていない前提」なので、確認が取れたら不明点と同じく確認済みに変えるのが自然なため
補足：仮定が誤りだった場合の扱い（取り消し・修正）は作っていない

### レビューのルール

#### ルールは、画面ではなくService Objectに書く
理由：画面を変えても、別の入口（APIなど）から呼ばれても、ルールが必ず守られるため
補足：RequestTicketReview / ApproveTicket / SendBackTicket / ResolveTicketItem。どれもチケットや項目をロックしてから判断し、同時に操作されても二重に処理しない

#### 不明点が残っていたらレビュー依頼に進めない。仮定は残っていても進める
理由：設計の目的どおり、不明点はレビューの前に解消させたい。仮定は「この前提で進める」ことをレビューで確かめてもらう対象なので止めない

#### 差し戻しの理由は、不明点としてチケットに追加する
理由：理由を解決するまで、もう一度レビュー依頼に進めなくなる。「不明点が残っていたら進めない」ルールが、そのまま再レビューの条件として働くため
他の選択肢：コメントとして残す（再レビューの条件にはならない）

#### 完了・差し戻しはレビュアーだけ。レビュー依頼した本人はできない
理由：自分で依頼して自分で完了にできると、レビューの意味がなくなるため
補足：「誰が依頼したか」は、変更履歴の最後のレビュー依頼で判断する。レビュアーが1人しかいないチームでは完了できなくなる

### アカウントと権限

#### 管理者は、ロール（担当者・レビュアー）とは別の印にする
理由：小さなチームでは、レビュアーと管理者を同じ人が兼ねることが多いため
他の選択肢：ロールの1つにする（レビュアー兼管理者を表せない）

#### アカウントは管理者が作り、仮パスワードを発行する。メールでの再設定は作らない
理由：メール送信の仕組みを用意せずに済む。仮パスワードはサーバーで作り、画面に1回だけ表示する（DBにはハッシュしか残らない）
補足：仮パスワードでログインしたあとの変更の強制、ロールを変える画面は作っていない

#### アカウントは削除しない
理由：変更履歴が「誰が操作したか」を持っているため。消すと履歴がたどれなくなる

### ログインとセキュリティ

#### ログインはCookieのセッションで保ち、セッションはDBに記録する
理由：画面とAPIはViteのプロキシ（本番では同じドメイン）で同じオリジンになるので、トークンを画面側で扱わずに済む。DBに記録することで、ログアウトやパスワード変更のときにサーバー側で無効にできる
他の選択肢：CookieStoreだけにする（作りは簡単だが、盗まれたCookieをログアウト後も使われてしまう）

#### セッションの期限は、無操作2時間・最長12時間
理由：放置された端末からの操作を防ぐ。最長期限は、操作を続けていても定期的にログインし直させるため
補足：パスワードを変えると、その人の全セッションを消す（変えた本人の端末だけは新しいセッションを作り直す）

#### CSRF対策は、JSON以外の変更系リクエストを断ることで行う
理由：ほかのサイトのフォームはJSONを送れず、JSONを送るにはCORSの許可が要る。このAPIはCORSを許可していない。CookieにはSameSite=Laxも付けている
前提：この対策は「CORSを許可しない」「GETで状態を変えない」「画面とAPIを同じオリジンで提供する」の3つが崩れないことに頼っている。別ドメインから画面を配信するなどでCORSを許可するときは、CSRFトークンに切り替える

#### ログイン試行は、IPごと（3分に10回）とメールアドレスごと（15分に5回）の両方で制限する
理由：IPを変えながら1つのアカウントを狙う攻撃も防ぐため
補足：回数は、開発・テストではプロセスのメモリ、本番では Rails.cache に数える。本番でサーバーを複数台にするときは、全台で共有するキャッシュ（Solid Cache や Redis など）を設定すること

#### パスワードは12文字以上
理由：has_secure_password は上限（72バイト）しか確かめず、1文字でも登録できてしまうため

### 変更履歴

#### 変更履歴は、操作と同じトランザクションで記録する
理由：操作だけ成功して履歴が残らない、ということを起こさないため
補足：変更前後などの内容は jsonb の details に入れる。列名を changes にしないのは、ActiveRecord の同名メソッドとぶつかるため

#### 詳細画面の変更履歴は、開いたときに読み込む
理由：履歴は毎回見るものではないため。開いている間は、操作のたびに読み直す

### 画面

#### UIはGoogle（Material Design 3）寄りにし、UIライブラリは使わない
理由：シンプルに保つため。色・余白・角丸は index.css のトークンだけを使い、部品のCSSに色の値を直接書かない
補足：不明点＝赤、仮定＝黄、確認済み＝緑は意味を持つ色として、ほかの用途に使わない。ボタンは「主な操作（塗り）」「ふつうの操作（枠線）」「取り消し（文字）」の3種類

#### 一覧の絞り込みは、URLに持たせる
理由：リロードしても、URLを人に渡しても同じ一覧を出せるため

#### 一覧の不明点の数は、サブクエリで1回のSQLにまとめて取る
理由：チケットごとにSQLを発行しないため（[ticket_id, kind] のインデックスが使える）

#### 検証エラーは日本語で返す。訳は config/locales/ja.yml に自分で書く
理由：画面にそのまま出すため。rails-i18n などのgemは入れず、このアプリで使う分だけを書く

### 技術

#### DBはPostgreSQLにする
理由：変更履歴に「変更前後の値」を保存したい。PostgreSQLのjsonbなら、項目が増えても列を増やさずに保存でき、検索もできる
他の選択肢：MySQL（JSONは扱えるが、使い慣れたPostgreSQLを優先した）

#### Railsは8.1系を使う
理由：brakemanが、7.2系のサポート終了（2026年8月）を警告したため。8.1系はセキュリティ修正が2027年10月まで続く
他の選択肢：警告を無視する設定にする（CIは緑になるが、古いバージョンのまま放置することになるため選ばなかった）

#### Viteは5系に固定する（8系は使わない）
理由：Vite 8系が内部で使うrolldownの実行ファイルが環境によって正しく取得できず、npm run devが起動しないバグに遭遇したため。Vite 5系は実績のあるesbuild + Rollupの構成で、安定して動く
他の選択肢：Node.jsをアップデートして8系のまま使う（今回は動作の安定を優先して5系にした）

#### brakemanの警告は、理由を書いたうえで除外することがある
理由：管理者用のアカウント作成APIは、role と admin を受け付ける必要がある。管理者以外は403にしていて、テストでも確かめている
補足：除外は config/brakeman.ignore に、理由（note）付きで置く

### 公開（デモ）

#### 画面とAPIを1つのサービスで配信する（Dockerfile.production）
理由：Reactをビルドした画面をRailsの public/ に入れて一緒に配信すると、画面とAPIが同じオリジンになり、CSRF対策の前提をそのまま守れるため。画面のURL（/tickets/1 など）を直接開いても、Railsが index.html を返す
他の選択肢：画面を別のサービス（静的サイト）で配信する（CORSを許可する必要があり、CSRFトークンへの切り替えが要る）

#### 公開先はRenderにする（render.yaml）
理由：GitHubとつなぐだけで、pushのたびに公開される。Webサービス・PostgreSQL・毎日のリセット（Cron Job）を1つの設定ファイルにまとめられる

#### 公開するデモは、毎日リセットし、パスワードを変える操作を止める（DEMO_MODE=1）
理由：READMEにデモのアカウントを載せるので、誰でもログインできる。パスワード変更や仮パスワードの発行を許すと、誰かにログインできなくされてしまう。不適切な書き込みも、毎日のリセットで消える
補足：bin/rails demo:reset は、DEMO_MODE=1 のときしか動かない（本物のデータを消さないため）

## 作らなかったもの

- 担当者（チケットごとの担当者）：最初のテーブル案にはあったが、使い方が固まらないまま増やさなかった
- Markdownでの書き出し：一度作ったが、中心の機能ではないので外した
- ログインの成功・失敗の記録、メールでのパスワード再設定、二要素認証
- 添付ファイル、通知、全文検索などのRedmineにある機能全般
